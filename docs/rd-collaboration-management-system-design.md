# 多子项目研发协同管理系统设计方案

## 1. 背景与目标

你当前管理的是“一个大型集成软件 + 十几个子项目”的研发体系。典型痛点通常是：

- 子项目流程不一致，里程碑口径不统一；
- 质量数据分散在不同工具中，无法统一监督；
- 转测节点缺少强制卡点，质量风险晚暴露；
- 评审与发布靠线下沟通，过程可追溯性弱；
- 管理层缺少“项目群视角”的实时看板。

本系统目标是建设一个**项目群级别的一体化研发治理平台**，实现：

1. 统一过程规范（可配置、可复用）；
2. 统一质量监督（自动采集、自动预警）；
3. 统一转测卡点（自动校验 + 审批留痕）；
4. 统一评审发布（流程闭环 + 变更审计）；
5. 统一数据底座（打通各子系统数据源）。

---

## 2. 设计原则

1. **平台化**：上层统一标准，下层允许子项目按模板扩展。
2. **配置化**：流程、卡点、指标、通知规则均支持配置。
3. **自动化**：优先用系统自动采集、自动判定，减少人工填报。
4. **可追溯**：每个关键动作都有日志、审批人和时间戳。
5. **渐进落地**：先做 MVP，再扩展高级能力（预测、智能预警）。

---

## 3. 组织与角色模型

建议采用“项目群 - 子项目 - 迭代”三级治理结构。

### 3.1 角色建议

- 项目群经理（Program Manager）
- 子项目经理（Project Manager）
- 架构师 / 技术负责人
- 测试负责人 / QA
- 发布经理 / 运维
- 质量监督管理员（Quality Admin）
- 流程管理员（Process Admin）
- 审计/管理层只读角色

### 3.2 权限原则

- 基于 RBAC（角色）+ ABAC（数据范围）；
- 支持“项目群级”和“子项目级”双层授权；
- 关键操作（放行、驳回、豁免）必须二次确认并留痕。

---

## 4. 总体架构设计

## 4.1 逻辑分层

1. **接入层**：Web 管理端、移动审批端、API 网关；
2. **业务层**：流程规范、质量监督、转测卡点、评审发布、报表；
3. **集成层**：连接 Git、需求、测试、CI/CD、代码质量、安全扫描系统；
4. **数据层**：业务库 + 指标库 + 事件日志库；
5. **治理层**：权限、审计、告警、可观测性、配置中心。

## 4.2 核心服务建议

- `program-service`：项目群/子项目管理；
- `workflow-service`：流程模板与状态机；
- `quality-service`：质量指标采集、阈值预警；
- `gate-service`：转测/发布卡点规则与判定；
- `review-release-service`：评审会议、变更单、发布单；
- `integration-hub`：第三方系统连接器与数据同步；
- `report-service`：看板、报表、导出；
- `auth-audit-service`：统一鉴权与审计日志。

---

## 5. 核心功能模块

## 5.1 项目群协同中心

- 统一维护项目群、子项目、负责人、计划里程碑；
- 支持跨子项目依赖关系管理（前置/后置）；
- 输出统一甘特图和关键路径风险视图。

## 5.2 过程规范中心

- 定义研发流程模板（需求 -> 设计 -> 开发 -> 联调 -> 转测 -> 发布）；
- 支持不同子项目选择不同模板变体；
- 规范每阶段必备交付物（文档、报告、记录）。

## 5.3 转测卡点中心（重点）

每次“开发转测试”触发自动校验，未达标不可流转：

- 代码分支策略符合要求（例如必须走 MR/PR）；
- 单元测试通过率达到阈值；
- 核心模块覆盖率不低于阈值；
- 阻塞级缺陷数为 0；
- 构建成功且可部署到测试环境；
- 测试计划和用例评审完成。

支持“临时豁免”流程：必须填写原因、影响评估、批准人、有效期。

## 5.4 统一质量监督中心（重点）

- 汇总 DORA + 质量指标：交付周期、变更失败率、缺陷逃逸率、回归通过率等；
- 支持项目群/子项目/迭代多维度下钻；
- 自动风险评分（绿/黄/红）；
- 预警策略：阈值触发、趋势异常、连续恶化触发。

## 5.5 评审与发布中心（重点）

- 评审类型：需求评审、设计评审、测试评审、发布评审；
- 会议纪要、结论、整改项统一沉淀；
- 发布单与变更单关联（版本、范围、回滚方案、窗口期）；
- 发布后自动回写结果（成功/失败/回滚）。

## 5.6 数据源集成子系统（重点）

统一连接并标准化外部系统数据：

- 需求/任务：Jira、禅道、Azure DevOps；
- 代码与 MR/PR：GitLab/GitHub；
- CI/CD：Jenkins、GitLab CI、GitHub Actions；
- 质量与安全：SonarQube、SAST/DAST 平台；
- 测试：TestRail、禅道测试模块；
- 运维与监控：Prometheus、APM、日志平台。

提供两种同步方式：

1. **实时事件流**（Webhook + 消息队列）；
2. **定时批同步**（补偿、对账、重放）。

## 6. 端到端流程（示例）

## 6.1 从开发到转测

1. 开发完成后发起“转测申请”；
2. 系统自动拉取相关 MR、构建、覆盖率、缺陷数据；
3. 执行卡点规则判定；
4. 全部通过则自动流转到测试阶段；
5. 若不通过，给出失败明细并退回整改；
6. 如申请豁免，进入 QA 负责人 + 项目经理审批。

## 6.2 从测试到发布

1. 测试完成后发起“发布评审”；
2. 自动检查：
   - 高优先级缺陷是否清零；
   - 回归结果是否达标；
   - 发布包是否签名并可追溯；
   - 是否具备回滚预案；
3. 评审通过后生成发布单并进入发布窗口；
4. 发布完成自动写回状态并归档所有证据链。

---

## 7. 数据模型设计（核心实体）

建议最小实体集合如下：

- `Program`（项目群）
- `SubProject`（子项目）
- `Iteration`（迭代/里程碑）
- `WorkItem`（需求/任务）
- `CodeChange`（MR/PR）
- `BuildRecord`（构建记录）
- `TestRun`（测试执行）
- `Defect`（缺陷）
- `QualityMetricSnapshot`（质量指标快照）
- `GateCheck`（卡点检查）
- `ReviewRecord`（评审记录）
- `ReleaseTicket`（发布单）
- `ExemptionRecord`（豁免记录）
- `AuditLog`（审计日志）

关键关系：

- 一个 `Program` 包含多个 `SubProject`；
- 一个 `SubProject` 绑定一个流程模板和多套卡点规则；
- 一个 `ReleaseTicket` 关联多个 `BuildRecord`、`TestRun` 与 `ReviewRecord`；
- 所有关键节点均写入 `AuditLog` 形成追溯闭环。

## 8. 卡点规则配置建议

规则引擎建议采用“规则表达式 + 策略版本化”模式。

示例（伪 YAML）：

```yaml
gate_name: dev_to_test
project_scope: subproject-A
version: 1.3.0
rules:
  - key: build_success
    expr: build.status == "SUCCESS"
    severity: blocker
  - key: unit_test_pass_rate
    expr: test.unit_pass_rate >= 0.95
    severity: blocker
  - key: code_coverage_core
    expr: quality.core_coverage >= 0.80
    severity: warning
  - key: blocker_defect_count
    expr: defect.blocker_open == 0
    severity: blocker
exemption:
  enabled: true
  approvers: ["qa_lead", "project_manager"]
  expire_in_hours: 72
```

## 9. 指标体系与管理看板

## 9.1 项目群级 KPI（建议）

- 迭代准时率（按计划完成）；
- 转测一次通过率；
- 发布一次成功率；
- 严重缺陷逃逸率；
- 平均修复周期（MTTR）；
- 变更失败率（CFR）；
- 关键流程合规率（按模板执行）。

## 9.2 看板分层

- 管理层看板：风险热力图、红黄绿状态、跨项目对比；
- 项目经理看板：进度偏差、卡点失败原因 TopN；
- 研发/测试看板：每日缺陷趋势、构建与测试健康度。

---

## 10. 非功能需求

- 可用性：核心功能可用性 >= 99.9%；
- 性能：关键页面 95 分位响应 < 2s；
- 扩展性：支持 20+ 子项目并行；
- 安全性：统一 SSO、操作审计、敏感字段脱敏；
- 合规性：审计日志不可篡改、关键数据可追溯。

---

## 11. 技术实现建议（可落地）

## 11.1 推荐技术栈（示例）

- 前端：React + TypeScript + Ant Design；
- 后端：Java/Spring Boot 或 Node.js/NestJS（微服务或模块化单体）；
- 存储：PostgreSQL（业务）、Redis（缓存）、对象存储（附件）；
- 集成：Kafka/RabbitMQ + Webhook；
- 流程：Camunda/Flowable（BPM）或自研状态机；
- 可观测：Prometheus + Grafana + OpenTelemetry。

## 11.2 集成策略

- 每类外部系统实现标准 `connector` 接口；
- 统一数据映射到内部领域模型；
- 失败重试 + 死信队列 + 对账任务确保数据一致性；
- 对外暴露标准 API，便于后续扩展和二次开发。

## 12. 分阶段实施路线（建议 4 期）

## 阶段 1（1-2 个月）：MVP

- 项目群台账 + 子项目流程模板；
- 转测卡点基础规则；
- 对接 Git + CI + 缺陷系统；
- 基础看板（进度、缺陷、构建）。

## 阶段 2（2-3 个月）：治理强化

- 质量监督中心上线；
- 评审管理（需求/设计/测试）；
- 豁免审批闭环 + 审计追溯；
- 告警通知（企业微信/邮件）。

## 阶段 3（2 个月）：发布闭环

- 发布评审与发布单联动；
- 回滚与变更记录闭环；
- 发布质量复盘报告自动生成。

## 阶段 4（持续优化）：智能化

- 风险预测（基于历史数据）；
- 卡点策略智能推荐；
- 管理层经营分析与资源优化建议。

---

## 13. 风险与应对

- **风险：流程推动阻力大**  
  应对：从 2-3 个试点子项目先行，模板成熟后推广。

- **风险：系统集成复杂度高**  
  应对：采用“连接器标准 + 分批接入 + 先关键后完整”策略。

- **风险：数据口径不一致**  
  应对：建立统一指标字典和口径管理委员会。

- **风险：卡点过严影响效率**  
  应对：区分 blocker/warning，并设置可审计豁免机制。

---

## 14. 立项验收标准（建议）

满足以下条件可判定系统一期成功：

1. 覆盖不少于 80% 子项目；
2. 转测一次通过率提升 >= 20%；
3. 发布失败率下降 >= 30%；
4. 关键流程合规率 >= 95%；
5. 管理层可在单一看板查看项目群实时状态。

---

## 15. 你可以马上启动的动作清单

1. 先确定 3 个试点子项目；
2. 明确统一流程模板与卡点最小集合；
3. 选定首批集成系统（建议 Git + CI + 缺陷）；
4. 设定一期 KPI 与验收时间点；
5. 建立项目群治理例会（周会 + 月度质量评审）。

这份方案可以直接作为你后续的立项文档骨架，再由各职能负责人补充细化规则和字段口径。
